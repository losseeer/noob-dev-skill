# 项目开发状态树协议（Development Tree Protocol）

> 本文件是 `dev-companion` skill 的能力 A：**always-on**，只要在开发就必须维护。
> 它是一个 decision tree（决策树）：记录「我们在这步定了什么 → 接下来做什么」。
> 它不是 WBS（work breakdown structure，工作分解结构）：父子不是「整体包含部分」，而是「上一步的决策长出下一步」。

---

## 1. 文件布局

```
<project-root>/
└── dev-tree/
    ├── TREE.md              # 唯一真源（single source of truth）
    └── versions/
        ├── 001-init.md
        ├── 002-skeleton.md
        └── 003-db-choice.md
```

- **单一真源 = `TREE.md`**。mermaid 图、ASCII 树、进度条这类可视化**只能由 `scripts/check_tree.py` 生成**，禁止手写第二份副本——手写副本一定和真源漂移。
- 产物（`TREE.md`、`versions/*.md`）**只描述项目本身**。禁止在里面写「根据 dev-companion 规范第 X 条」这类协议元信息，那是泄漏，用户不需要知道。

---

## 2. 节点的最小契约（放宽了格式，只留三条）

书写方式自由（编号、加粗、emoji、行尾备注都允许），机器只认这三件事：

| 契约 | 要求 | 为什么 |
|---|---|---|
| **C1 状态** | 每一行节点必须是 Markdown checkbox：`- [x]`（已完成）/ `- [ ]`（待完成） | checkbox 就是状态本身，渲染成勾选框最直观，且 `git diff` 里一眼看出变化 |
| **C2 版本链接** | 每个节点必须含一个指向 `versions/*.md` 的 Markdown 链接，如 `[v003](versions/003-db.md)`。**链接文案必须是 `v` + 三位数字**（`v003`），脚本靠这个格式识别引用 | 节点链到「当时的项目版本文档」，可回溯；格式不统一会导致 E9 误判 |
| **C3 层级** | 父子关系由**缩进**（格式 A）或**点分 ID**（格式 B）表达 | 脚本据此重建树并校验不变量 |

其余内容脚本一律忽略，你想写多啰嗦都行。

### 格式 A（默认）：缩进 checkbox 列表

```markdown
- [x] 启动：确认目标与技术栈 — [v001](versions/001-init.md)
    - [x] 搭最小骨架，能本地跑起来 — [v002](versions/002-skeleton.md)
        - [ ] 加数据持久化 — [v003](versions/003-db.md)
    - [ ] 接入真实的邮件发送 — [v004](versions/004-mail.md)
```

缩进必须是 2 或 4 空格（整个文件统一即可，脚本自适应），禁止跳级。

### 格式 B（可选）：扁平表格 + 显式 ID

当预计层级 > 4 层时用 B。列表缩进到第 5 层就难读，表格不会。

```markdown
<!-- dev-companion:tree format=table -->

| ID | 状态 | 节点 | 版本 |
|---|---|---|---|
| 1 | [x] | 启动：确认目标与技术栈 | [v001](versions/001-init.md) |
| 1.1 | [x] | 搭最小骨架，能本地跑起来 | [v002](versions/002-skeleton.md) |
| 1.1.1 | [ ] | 加数据持久化 | [v003](versions/003-db.md) |
| 1.2 | [ ] | 接入真实的邮件发送 | [v004](versions/004-mail.md) |
```

层级由 ID 的点分位数决定（`1.1.1` 的父是 `1.1`），与表格行顺序无关（脚本会先扫全量 ID 再校验父子，所以乱序写也可以）。切换格式要添加或删除 `<!-- dev-companion:tree format=table -->` 标记行，并同步重写整个表。

> **推荐值**：默认用 A；当同一条链路上的决策预计超过 4 次时，改用 B。不要在两种格式之间来回切。

### TREE.md 的头部（必填）

```markdown
# <项目名> · 开发状态树

> 当前活动节点：`加数据持久化` → [v003](versions/003-db.md)
> 最近校验：2026-10-05 · `python <skill 目录>/scripts/check_tree.py .` → PASS（4 节点 / 2 已完成）
```

「当前活动节点」是全树唯一的指针，指到**现在正在做的那个待完成叶子**。多个待完成叶子允许存在（用户排到后面还没做的），但当前只有这一个在推进。

**终止态**：全部节点都标 `[x]` 之后没有待完成节点可指了，此时写成：

```markdown
> 当前活动节点：—（全部完成）
```

脚本认这个写法，不会再报 E8。但**声称全部完成而树上仍有待完成节点**会报 E8——
别用终止态来掩盖没做完的事。

## 3. 不变量（invariants）

每次改完树都要满足。**但请注意：脚本只判定其中一部分，剩下的靠人工自律**——
拿到 PASS 不等于全部不变量都过了，下表最后一列写清楚了谁负责。

| # | 不变量 | 来源 | 谁判定 |
|---|---|---|---|
| **I1** | 待完成节点一定是叶子节点 | 你的原话 | 脚本（E1、E6 跳级） |
| **I2** | 每个节点至少一个指向 `versions/` 的链接；`versions/` 下不得有孤儿文档；版本标签不重复 | 由「每节点记录当前状态并链到版本文档」推出 | 脚本（E2/E3/E4/E5） |
| **I3** | 头部必须声明「当前活动节点」，且它必须是树中真实存在的、**待完成**的节点 | 本 skill 补：否则下一次进入项目不知道从哪里接着干 | 脚本（E8） |
| **I4** | 兄弟节点自上而下的顺序 = 用户决定的执行顺序 | 本 skill 补：让顺序承载信息，而不是靠记忆 | **人工**（脚本无法判断顺序是否合意） |
| **I5** | 一个节点只有在「自己的交付目标已达成并验证」后才能标 `[x]` | 本 skill 补：防止把没做完的事标成完成 | 脚本只查第 2 条（E7）；第 1、3 条**人工**（见第 5 节） |
| **I6** | 任何编号引用必须可定位：节点 ID、版本标签、候选名、`§x.y` 出现时，必须同时给出能定位到它的锚点 | 本 skill 补：编号只在产生它的那处有意义，脱离上下文就是悬空引用 | 脚本查「标签存在性」（E9）、「是否写成链接」（W4）、「候选表落地节点列」（E10）；候选名引用、章节 `§x.y` 引用**人工** |

> **不要拿 PASS 当放行条。** PASS 只意味着 E 级错误为零。I4、I5 的第 1/3/4 条、
> I6 的候选与章节引用，脚本一行都没看。

### I1 带来的真实冲突，以及处置

「待完成必须是叶子」和「遇到决策点就在当前节点下开子树」会打架：当前活动节点本身是待完成叶子，直接加子节点就违反 I1。

**处置（推荐，默认路径）**，三步：

1. 进行中的节点 X 遇到会产生新任务的决策点；
2. **先把 X 的标题改写成「已达成的事实」**（例如把 `实现用户模块` 改成 `实现用户模块：方案定稿`），此时它的交付目标 = 一份确定的方案，确实已达成；
3. 给 X 标 `[x]`，**然后**在 X 下建子节点。

禁止的操作：**对一个尚未达成的目标标 `[x]`**。这是把状态写脏的唯一通道，必须堵住。

**降级路径**：如果决策是参数级的、不产生任何新执行任务（例如「按钮用蓝色还是绿色」「端口用 8080 还是 3000」），**不开子树**，只在当前节点的版本文档里追加一条决策日志。推荐这么做，否则树会被琐碎选择淹没到不可读。

### I6 的细则：四类编号怎么引用

编号本身不提供任何定位能力，只有**锚点**（链接 / 全标题 / 归属）才提供。

| 引用对象 | 禁止的裸写法 | 正确写法 |
|---|---|---|
| 节点 | 「1.2.1 做完了」 | 「1.2.1『加数据持久化』→ [v003](versions/003-db.md) 做完了」 |
| 版本标签 | 「见 v003」 | 「见 [v003](versions/003-db.md)」——至少写成链接 |
| 候选 | 「选 B」 | 「选 v003 的候选 `302-redirect`」——候选编号是**决策点局部**的，跨轮次引用必须带归属 |
| 章节 | 「按 §3.2 办」 | 「按 `tree-protocol.md` §3.2（对应节点 v003）」——`§x.y` 必须写明出自哪份文档 |

三条硬要求：

1. **候选用 slug 命名，不要用 A/B/C。** slug（把标题压成小写短横杠的 URL 安全短串，源自报业 slug line）让候选名自带语义：`302-redirect` / `301-redirect` 在任何时候都不会歧义，`A` / `B` 会。这是可选的可读性改进，**不是追踪手段**。
2. **候选表必须有「落地节点」列**（见第 6 节）：D1（方案选型）下，推荐行链到它产生的节点、落选行写「不产生节点」；D2（任务排序）下，候选通常**只是排到后面而非被淘汰**，所以每行都要链到它最终对应的节点，只有用户明确说不做才写「不产生节点」。追踪能力来自这一列，不来自命名。
3. **跨轮次、跨文档引用候选必须带决策点归属**（节点号或版本标签）。用户隔几轮回一句「就用 B」时，没有归属就无法消歧，此时应当回问，不要猜。

> **可校验边界（如实说明）**：`check_tree.py` 只能自动校验「版本标签是否存在」（E9）和「是否写成了链接」（W4）。**候选名引用、`§x.y` 引用、聊天窗口里那句「选 B」都无法自动校验**，只能靠本规则约束行为。不假装脚本能全覆盖。

## 4. 决策点协议（decision point）

「决策点」只有两种（你的定义）：

- **D1 方案选型**：向用户提问「选哪个实现方案」
- **D2 任务排序**：向用户提问「这么多任务，先做哪个」

处理流程：

1. **识别**：我准备开口问用户选择题了 → 这就是决策点。
2. **提问**：候选 ≤ 3 个，每个候选一句话写清代价，**必须给出推荐值并说明推荐理由**。一次只推进一个决策点，不并列轰炸。候选**用 slug 命名**（`302-redirect`）而非 `A/B/C`。
3. **落地**（用户回答后，按顺序做）：
   - 把候选对比表写进**当前节点已有的那份版本文档**（这个决策就发生在它这里）。**不要另外新建一份**——新建的那份没有任何节点指向它，会触发 E4 孤儿文档；
   - 按第 3 节的处置改写当前节点标题 → 标 `[x]` → 在其下建子节点：
     - D1：节点 = 选定方案的落地任务（可拆成多个子任务）
     - D2：节点 = 用户排好序的那批任务，建成**兄弟**（挂在同一个父节点下），自上而下即用户决定的顺序
   - **给每一个新建的子节点各建一个版本文档**（`NNN-slug.md`，至少写交付目标 + 完成证据 = `未验证`）。**漏掉这一步会直接触发 E2/E3 卡在校验**，流程走不下去。
   - 「落地节点」列怎么写，取决于决策类型：
     - D1（方案选型）：只有被选中的方案产生节点，落选行写「不产生节点」。
     - D2（任务排序）：候选通常**不是被淘汰、只是排到后面**，每行都要链到它最终对应的那个节点；只有用户明确说「这个不做了」才写「不产生节点」。
   - **用户明确放弃的候选：删除该节点**（你的原话）。删除指的是从树里移除该节点及其子树；它对应的版本文档同步删除，并在父节点版本文档的「已放弃方案」里留一行说明，免得日后重复讨论同一个坑。
   - 更新头部「当前活动节点」指向新建的第一个待完成叶子。
4. **落地后**：跑一次校验再向用户汇报。**不允许先爽快地汇报、树留着以后补。**

### 两个协议空白怎么填

- **用户中途追加一个需求**（不是任何候选项，是临时想起来的）：同样按 D2 处理——
  就当是问用户「这个新任务排到哪」，用户定了顺序后在活动节点下开子树。**不要在树上凭空插节点**，
  否则这条父子边找不到对应的决策，树就变成流水账了。
- **一个候选产出多个节点**（如 `302-redirect` 同时产出了「实现跳转」和「生成短码」）：
  「落地节点」列写**主节点**（链路的起点），其余节点在本节「下一步 / 未决」里列全并链上。
  追踪靠这一列 + 下一步的链接，缺一个就会断。

## 5. 节点完成协议

一个节点标 `[x]` 之前必须同时满足：

1. 它的交付目标（写在版本文档第 1 节）已实现；
2. 有**完成证据**：验证命令 + 实际输出摘要，写进版本文档的「完成证据」节。**没有写「未验证」，不允许留空**；
3. 更新 TREE.md 头部的最近校验行。

**版本文档是快照，不是活文档。** 「项目状态」节写的是**写入那一刻**的状态，之后不回改——
改了就不是快照，回溯也就失效了。当前状态始终看 `TREE.md`。

## 6. 版本快照文档（version snapshot）

模板见 `assets/version.template.md`。字段契约：

候选对比表的列固定为：`候选 | 做法 | 好处 | 代价 | 结论 | 落地节点`。最后一列不允许省略或留空。
D1（方案选型）下落选行写「不产生节点」；D2（任务排序）下落选行通常只是排到后面，要链到它最终对应的节点（见第 4 节）。

**字段要求：**

| 字段 | 要求 |
|---|---|
| 交付目标 | 一句话、**可验证**。写不出「怎么算做完」就别建这个节点 |
| 决策记录 | 若本节点由决策点产生：候选对比表（含「落地节点」列）+ 用户选择 + 理由；否则写「无」 |
| 项目状态 | 当时的文件清单、怎么跑起来、已实现什么 |
| 完成证据 | 验证命令 + 输出摘要；未完成时**显式写 `未验证`** |
| 下一步 / 未决 | 待办、被阻塞的点、下一步打算 |

**元信息区的 `git commit` 字段**（模板第 5 行）：

- 项目用了 git → 填写入那一刻的 commit hash（7 位以上）。**这是快照唯一能真正定位到代码状态的锚点**——
  没有它，版本文档只是一段文字描述，不是可恢复的状态点。
- 项目没用 git → 写 `none`。如实写，不要留空也不要编。

脚本只校验格式（W5：填了值但不是合法 hash，也不是 `none`）。
**hash 是否真实存在由 git 自己保证，脚本不去查**——查了也是慢且不必要。

## 7. 撤销与回退（reversal）

两件事长得很像，但处置完全相反，**先分清楚再动手**：

| 情况 | 处置 | 为什么 |
|---|---|---|
| **放弃一个还没开工的候选** | **删除**节点及其子树，版本文档同步删除（见第 4 节） | 这事从未发生，删掉合理 |
| **推翻一个已经做完的决策** | **保留历史**，加撤销记录 + 开新节点 | 这事已经发生，删掉就是伪造历史 |

树记录的是「我们做过什么决定」。**推翻一个决定本身也是一个新的决定**——
所以回退是**加记录**，不是抹掉记录。

### 撤销一个已完成的节点（流程）

假设节点 X 已标 `[x]`，现在发现它错了要推翻：

```text
① X 保持 [x] 不动 —— 它确实发生过。删节点或删版本文档 = 伪造历史（违反 H11）
② 在 X 的版本文档追加「## 撤销记录」：撤销时间、原因、改用哪种做法
③ 在 X 下新建子节点「撤销<X 的标题>：<新做法>」[ ]，建它的版本文档（完成证据写「未验证」）
④ 更新头部「当前活动节点」指向这个新节点
⑤ 跑校验，PASS 后再汇报
```

为什么挂在 X 下面：X 已完成，可以有子节点（I1 只约束待完成节点必须是叶子），
且撤销语义上就是 X 的后续——父子关系仍然表达「上一步的决定长出下一步」。

### 本 skill 不支持什么（如实说明）

- **不支持把项目状态回退到某个版本快照。** 版本文档是给人看的记录，不是可执行的恢复点。
  真要回退代码，用 git（`git revert` / `git checkout <hash>`）——`git commit` 字段就是给你这个 hash 的。
- **不支持把决策点「重新打开」重新选一次。** 要做的是加一个撤销节点走新方向，
  而不是把原来的决策节点改回 `[ ]`（那会让树上出现「这个决策到底算不算做过」的歧义）。
- **不支持撤销「撤销节点」以上的整条链。** 一次撤销只处理一个节点；要退整条链就逐个来。

## 8. 明确不采用的方案（边界记录）

| 方案 | 为什么不采用 |
|---|---|
| 一个节点一个 `.md` 文件，用目录表达层级 | 层级信息散落在文件系统里，看全貌要逐个打开；重命名/移动节点就是改目录结构，diff 难读。单文件 + 缩进在同样信息量下更好维护 |
| JSON / YAML 作为真源，md 只是渲染产物 | 新手用户直接手改 JSON 容易破坏格式；且失去了勾选框的直观性 |
| 手写 mermaid / ASCII 图并存 | 双写必漂移。改为脚本从单一真源生成 |
| 只写 git commit、不写版本文档 | commit 不能跨「还没提交的工作」表达状态，也不可读。两者互补：版本文档记决策与状态，`git commit` 字段指向那一刻的代码 |
| 用版本文档承担回退功能 | 它是给人看的记录，不是可执行的恢复点。回退代码归 git，见第 7 节 |
| 三状态（已完成 / 进行中 / 待完成） | 你明确只要两种。「进行中」= 头部「当前活动节点」指针指向的那个待完成叶子，用指针而不是第三种状态 |

## 9. 校验

```bash
# 用本 skill 目录里的脚本，不是用户项目里的（脚本不复制进用户项目）
python ~/.workbuddy/skills/dev-companion/scripts/check_tree.py <project-root>            # 人读输出
python ~/.workbuddy/skills/dev-companion/scripts/check_tree.py <project-root> --map      # 额外打印当前路径面包屑
```

用于覆盖 I6 里**可自动校验的那部分**：

- `E9`（error）：正文引用了树上不存在的 `vNNN` —— 悬空引用。
- `W4`（warning）：版本标签是裸写，没写成链接。
- `E10`（error）：候选表缺「落地节点」列，或推荐行的该列没写清落到哪个节点。
  **注意盲区**：只在文档确实写了候选表时才检查；文档压根没写候选表，
  脚本无从判断它是不是决策点产物。
- `W5`（warning）：版本文档的 `git commit` 字段填了值，但既不是合法 hash 也不是 `none`。
  只查格式，**不去验证 hash 在仓库里是否真实存在**（那是 git 的事）。

I6 里其余部分（候选名引用、`§x.y`、聊天里的「选 B」）**无法自动校验**，靠规则约束行为。

**第 7 节的撤销流程同样不校验**：脚本看不出「该不该撤销」，也看不出撤销记录写没写。
它只能保证撤销之后树的形状仍然合法（I1、I2 那些）。别把 PASS 当成「撤销做对了」。

退出码：`0` = PASS，`1` = 有 ERROR，`2` = 树文件不存在/不可解析（**这是硬失败，必须显式报告给用户，不许当成 PASS**）。

何时跑：**每次决策落地后、每个节点标完成时、每次撤销之后、每次会话结束前**。
