# 任务：执行自适应澄清

只问覆盖矩阵里排队的待问项，用生活化语言，不要求用户懂需求工程术语。

## 每轮格式

- 每轮最多 **3 题**。
- 每题给 A/B/C 选项；不足三个自然选项时只给 A/B。
- 每个选项用一句话说明实际影响（会多做/少做什么，代价是什么）。
- 每题最后提供 `其他（请填写）：______`。
- 对推荐选项明确标注「推荐」并给出依据。
- **先给结论再给题**：每轮开头用一句话说明「还差什么，问完这些就能定稿」。

## 提问规则

1. `conflict`：先列出互相冲突的原始证据原文，再问以哪个为准。
2. P0 `missing`：必须问，不能用默认值绕过（COV-001）。
3. `low_confidence`：只追问一句能区分结果的问题，不要连续追。
4. `undecided`：明确允许回答「还没想好」；随后采用推荐默认值，并记录触发重审条件。
5. `explicit`、可靠 `inferred` 和已接受的默认值：**不重复问**（COV-006）。
6. 用户自由文本回答优先于预设选项，并把原话写进 evidence。

## 超时与未授权的默认策略

用户直接说「你自己看着办」「先这样」、长时间不回答、或在自动化场景没有回答机会时：

1. 直接执行每题的 `recommendation`
2. 在对应维度写 `status: undecided`，并填入 `review_trigger`
3. 在 `open_questions` 里显式记一句「按推荐值处理，待用户确认」
4. **不要静默当成用户已确认**——这两件事必须区分开

## 回写规则

每轮回答后立即：

- 更新对应维度的 `status` / `value` / `evidence.source` / `reason` / `confidence`
- 删除已解决的问题
- 重跑冲突检测（新答案可能引入新冲突）
- 更新剩余问题队列

## 结束条件

全部满足才可结束：

- 没有 P0 `missing`
- 没有 `conflict`
- 所有 `undecided` 都有用户知情的默认值与复审触发条件

## 边界

- 不询问商业问题（定价、商业模式、要不要做）——那是项目定位 Skill 范围。
- 不询问技术选型（用什么框架、什么数据库）——那是设计阶段的事，除非技术约束本身就是需求。
- 不要把多个维度合并成一题塞给用户；一题只解决一个维度。

## 输出

要么输出下一轮问题（≤ 3 题），要么明确输出「覆盖矩阵已满足建模条件」并给出 `ready_for_modeling: true`。
