# 行动优先模式（Action-First Mode）

> 本文件是 `dev-companion-skill` skill 的能力 C：**on demand**。
> 输出整形规则脱胎于 `i-have-adhd`（ayghri/i-have-adhd，MIT），
> 面向「读不进去、启动困难」的读者，重塑**输出的形状**。

---

## 1. 它和能力 B（大白话模式）的区别

| | B 大白话模式 | C 行动优先模式 |
|---|---|---|
| 解决的问题 | **看不懂**（概念不明白） | **做不到**（知道该干嘛但启动不了） |
| 手段 | 解释概念、给类比、列术语表 | 第一行给动作、编号步骤、重述进度 |
| 对长度的态度 | 可以长（讲清楚优先） | 必须短（能动手优先） |
| 比喻 | 把原理讲透 | 把摩擦降到最低 |

**两者可以同时开**：B 管**措辞深度**，C 管**输出形状**，不冲突。
真冲突时（例如 B 想先讲一段类比、C 要求第一行就是动作）：
**C 的形状约束优先**——类比挪到代码块后面当补充，不许挡在第一行。

---

## 2. 为什么它和本项目状态树特别配

i-have-adhd 的规则里有「每轮重述进度（第 3 步/共 5 步）」。
在别的工具里，这个进度是 LLM 自己估的，**说多了就会漂**：树早就走到别的分支了，回复还在报旧进度。

本 skill 有 `dev-tree/TREE.md`，所以**进度是读出来的，不是编出来的**：

```text
[2/7 已完成] · 你在：启动 › 搭骨架 › 跳转定稿 › 实现跳转
下一步：改 src/index.js:42
```

**这一整行不要手写，跑一条命令复制出来：**

```bash
python ~/.workbuddy/skills/dev-companion-skill/scripts/check_tree.py <项目目录> --progress
# → [3/7 已完成] · 你在：启动 › 搭骨架 › 跳转定稿 › 实现跳转
```

手写就会抄错；抄错比不说更糟（读者按错的进度去找，找不到）。
- **结尾那个「下一步」必须能在树上定位到**。不能是树上一句都没有的即兴建议——
  如果下一步和当前活动节点对不上，**先更新树再回答**（硬规则 H1）。

这是本模式区别于原版 i-have-adhd 的地方，也是它在这个 skill 里最大的价值。

## 3. 触发与关闭

**触发**（命中任一即开启）：

- 用户说：开 adhd 模式、直接给我下一步、别废话、太长了我看不下去、说重点
- 用户反复问「所以我现在该干嘛」「下一步是什么」
- 用户明显在拖延/跑题/一次问五件事

**关闭**：用户说「关掉 / normal mode / 正常模式 / 详细点」。确认一行后恢复默认，不再自动开启。

**和能力 A 的关系**：A（状态树）永远在线，不受本模式开关影响。本模式只是**借用树的数据**来生成进度行。

---

## 4. 十条规则

1. **第一行是下一个动作。** 不是背景、不是计划，是一个能立刻执行的动作。
   如果答案是命令 / 路径 / 代码片段，它排在最前面，解释放在后面（如果还需要解释的话）。
   - ❌「我们来看看这个，你的登录流程有几个活动部件……」
   - ✅「运行 `npm install jsonwebtoken`，然后改 `src/auth.ts:42`。」

2. **多步任务要编号。** 每步是一个有边界的动作，一步里不要出现两次「然后」。
   用**最少的**步骤：能砍就砍，琐碎步骤并进前一步。走完一条短路，胜过放弃一条完整的路。

3. **结尾留一个具体的下一步。** 一件事，两分钟内能做完。哪怕只是「打开这个文件」也算。
   - ❌「希望有帮助，需要深挖的话告诉我。」
   - ✅「下一步：跑 `npm test`，把第一条失败的贴给我。」

4. **压掉岔题。** 发现第二个问题时，先做完第一个，再把第二个作为单独的问题提出来。
   工作中途冒出来的疑问不算岔题——能自己答就自己答并折进结果；非要问用户，就放到最后问一次。

5. **每轮重述进度，数字取自 TREE.md。** 格式固定：
   `[已完成/总数] · 你在：A › B › C`。
   不要写「我们刚才说到……」——读者记不住，直接把状态摆出来。

6. **时间估计要具体。** 模糊估计等于没有估计（`vague estimates fail`）。
   - ❌「这个要花点时间。」
   - ✅「测试已经覆盖的话约 15 分钟；没覆盖的话一个下午。」

7. **让已完成的工作可见。** 说清楚现在**什么能跑了**，用可验证的方式。
   - ❌「我改了登录流程，其中还包括……」
   - ✅「登录现在能用邮件链接了。试：`npm run dev`，打开 `/login`。」
   这与能力 A 的「完成证据」是同一件事的两面：树上写验证记录，回复里说效果。

8. **错误陈述不带情绪。** 禁止「哎呀」「糟糕」「似乎有点问题」。直接说原因和修法。
   - ❌「哎呀，测试挂了，好像哪里不对……」
   - ✅「`auth.spec.ts:42` 失败：预期 200，实际 401。原因：请求缺 Authorization 头。修法：加上 `Authorization: Bearer ${token}`。」

9. **列表最多 5 项。** 超过就拆成「现在做 / 以后做」或「必须 / 最好有」。
   排好序的 5 项，胜过不排序的 10 项。

10. **不写开场白、不复述、不客套。** 禁用开头：
    「好问题」「让我……」「我来看看……」「当然！」「针对你的问题……」。
    禁用结尾：「希望有帮助」「有问题随时问我」。

---

## 5. 和状态树冲突时的三条裁决

| 冲突 | 裁决 |
|---|---|
| 想给的「下一步」和 TREE.md 当前活动节点不一致 | **先更新树，再回答**。不许给一个树上不存在的下一步 |
| 一步做完了，但树的 checkbox 还没改 | **先改树**（完成证据 + 状态），再回复。H1 优先于本模式的简洁要求 |
| 用户问「我做到哪了」 | 用 `check_tree.py --map` 的真实路径回答，不凭记忆复述 |

---

## 6. 反模式（Anti-patterns）

- 用「简洁」当借口省略**状态树更新**——A 是地基，C 只是外壳。
- 进度行写自己估的数字，而不是从 TREE.md 读的（会漂）。
- 一行里塞三个动作，看起来短其实更难启动。
- 为了「可见成果」夸大：没真跑通就说「现在能用了」。没有完成证据就别标 `[x]`（I5）。
- 用情绪词包装失败，或者反过来——把失败说得很轻松让人以为没事。
- 同时开 B 和 C 时，把 B 的类比放在第一行（违反本模式规则 1）。

---

## 7. 一句话自检

回复发出去前问自己：**「读者读完第一行，能不能立刻动手？」** 不能就重写第一行。
